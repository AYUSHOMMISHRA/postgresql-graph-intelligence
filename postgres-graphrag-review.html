01

The Problem

Standard retrieval — keyword or vector search over document chunks — finds text that resembles the question. It cannot answer a question whose answer requires connecting two documents that never reference each other.

Concrete example, from this repository's own demo dataset

Document A: checkout-service depends_on auth-service. Document B: auth-service is owned_by Identity Team. Ask "which team owns the dependency of checkout-service?" and the answer — Identity Team — is never written as a single sentence anywhere in either document. It only exists as a two-hop chain, and similarity search has no mechanism for following it: neither document is more "similar" to the question than the other, and reading either one alone doesn't answer it.

This kind of relational question is routine in operational and knowledge-base settings — ownership, dependency chains, incident timelines — and today, connecting the dots is a manual step:

Current approachWhy it falls short
Manual tracing (grep, Slack search, asking a teammate)Works for one question at a time; doesn't scale as documents accumulate, and depends on someone already knowing where to look.
Vector-only RAGFast, but structurally can't chain facts across documents — measured directly in Measurable Impact.
A separate graph database alongside PostgresSolves the chaining problem, but adds a second datastore that has to be kept in sync with the source of truth.

A second, related problem: most systems that attach a citation to an answer only check that the citation exists in the retrieved set — never that the cited text actually supports the specific claim next to it. A reversed relationship, a wrong number, or a claim from an unrelated part of the same document can cite real evidence and still look fully "grounded." This is not a hypothetical: it's measured directly in Measurable Impact, using the industry-typical citation-marker-only check as the baseline.

Both problems compound the same way: the more documents there are, the more often an answer depends on connecting facts that live in different places, and the more expensive it becomes to verify that a system's citations actually mean what they claim.

02

AI‑Powered Approach

What was built: postgres-graph-rag, a Python library with a CLI, a browser demo (Studio), and an MCP server on top. It stores vectors, full-text search, relational metadata, and a property graph all in one PostgreSQL database (pgvector + pg_trgm) — no separate vector database or graph database to run or keep in sync. AI is used only where language understanding is actually required; everything else, including graph traversal, is a deterministic SQL query.

StepHow
Chunk & embedSplitter + provider embedding callAI
Extract facts (triplets)Structured-output LLM callAI
Resolve entitiespg_trgm candidates confirmed by embedding similaritySQL + AI confirms
Fuse retrievalReciprocal Rank Fusion, Postgres full-text + vectorSQL
Traverse the graphRecursive CTE, hop-decay × edge-weight scoringSQL
Check citationsExistence → entity match → quote/number match, then a model call only if still undecidedSQL, then AI
Compose the answerLLM writes the cited answer textAI

Step by step, from the current source: a document is split into fixed-size overlapping chunks (a plain character-window splitter, not a model) and embedded in one batched call to the configured provider. Chunks and a content hash are committed to Postgres in a single transaction, guarded by a transaction-scoped advisory lock so two concurrent ingests of the same document can't race into duplicate rows — the document is searchable immediately. Fact extraction runs afterward, outside that transaction: an LLM reads each chunk and returns structured subject–predicate–object triplets (a schema-constrained call, not free text), with bounded concurrency, retry with backoff, and a per-content-hash lease so a duplicate concurrent ingest doesn't pay for extraction twice. Extracted facts become graph edges; entity names are resolved so that near-duplicate mentions (matched by trigram similarity, confirmed by embedding similarity) merge into one node.

At query time, the question is embedded once, then matched by one of three modes: pure vector search, Postgres full-text search fused with vector search by Reciprocal Rank Fusion ("hybrid"), or that plus a bounded, recursive-SQL graph traversal seeded from the best-matching passage(s) ("hybrid‑graph"). All three retrieval modes are SQL, not further model calls. The final answer is composed by one more model call, instructed to cite every factual sentence with a [source#ordinal] marker. The system refuses to answer — before ever calling that model — if no evidence was retrieved, or if none of the identifiers named in the question (e.g. a service or deployment name) appear anywhere in the retrieved evidence.

Citation trust has two tiers. By default, a citation is accepted if it names a chunk that was actually retrieved — it does not check that the cited text supports the claim. An optional, stricter mode splits the answer into individual claims and runs each through citation, quote, number, and negation checks purely in Python; only claims still undecided after those checks are sent to a model, and every claim in one undecided batch goes in a single call, not one call per claim.

Why AI is necessary here: no deterministic method can read "auth-service is owned_by Identity Team" and recognize it as a fact worth linking — that step requires language understanding. But once the fact is a graph edge, walking it is a solved SQL problem; re-invoking a model at every hop, as some GraphRAG designs do, would pay repeatedly for something a recursive query already does deterministically. This design pays for a model exactly once per extracted fact, once per composed answer, and, in the stricter grounding mode, once more only for claims cheap checks can't resolve on their own.

Final result: a question whose answer spans multiple documents gets a single, cited answer — or an explicit refusal to answer, never a guess dressed up as one.

Two ways to try it without writing code

A CLI Playground (postgres-graph-rag-demo playground) and a browser Demo Studio (postgres-graph-rag-studio) both let anyone submit their own text and question to the real engine, in an isolated tenant, without touching the bundled scenario. Both call the same shared service module, so neither re-implements ingestion, retrieval, or cleanup on its own — see Reusable Documentation for commands.

03

Measurable Impact

Re-run for this review against a real local PostgreSQL instance and a real Gemini API key — nothing below is reused from a prior write-up without re-checking it. The comparison points are plain vector search and citation-marker-only checking: the two practices this project replaces.

Retrieval: does the graph hop help?

The repository's own 60-document / 120-question benchmark, re-run live:

Vector (baseline)HybridHybrid + Graph
Multi-hop questions, Recall@512.5%10.0%82.5%
All 120 questions, Recall@570.8%70.0%94.2%
p50 latency5.0 ms7.6 ms52.7 ms

On multi-hop questions specifically, the graph traversal step turns a 1-in-8 baseline into roughly 8-in-10. That gap is the entire justification for the graph layer; without it, this project has no advantage over any other Postgres+pgvector RAG setup.

Grounding: does a citation mean what it claims?

The repository's own 140-case grounding benchmark, re-run live:

Contradicted‑claim escapeUnsupported‑claim escapeCorrect-claim retention
Citation-marker-only (baseline)100%81.8%100%
+ deterministic checks (no model call)0%0%66.7%

"Escape rate" is how often a wrong or contradicted claim still passes as grounded. The citation-marker-only baseline — the industry-typical approach — lets essentially all contradicted claims through. Adding the deterministic checks closes that to zero, at a disclosed cost: a third of genuinely correct claims are now conservatively rejected rather than risk a false pass, entirely in cases requiring cross-citation reasoning that non-model checks structurally cannot do. A further layer meant to recover that cost with one batched model call is built and unit-tested, but has no live-provider benchmark run recorded — see Limitations.

Real bug, found while verifying the CLI for this review, fixed and re-tested

The documented ingest/query/evaluate commands failed with "POSTGRES_URL or --admin-url is required" even when --runtime-url was supplied directly and no admin access was ever used — all three commands computed an admin DSN and immediately discarded it. Fixed by switching them to the same runtime-only DSN resolver the CLI Playground already used for exactly this reason; re-run afterward with only PGR_RUNTIME_URL set, no POSTGRES_URL, and confirmed working end to end.

04

Limitations

What to weigh before relying on this beyond a demo or an internal tool — each of these was observed directly, not assumed.

Answer reliability — found this review, reproduced twice

Using the repository's own two demo documents (checkout-service’s dependency chain, split across two files exactly as in the Problem example), a real Gemini call was run twice against the question "Which team owns the dependency of checkout-service?" in hybrid_graph mode. Both times, retrieval and graph traversal correctly found the full two-hop chain (checkout-service → auth-service → Identity Team) and it was passed to the model as retrieved evidence. Both times, the model itself chose to abstain (abstain_reason: model_abstained) instead of composing an answer, despite having sufficient evidence. This is a real, reproducible reliability gap in the default lite-tier model's answer composition — not a retrieval defect, and not fixed as of this review. A separately recorded real run against OpenAI on a different four-question set returned 3 grounded answers and 1 similar safe abstention, suggesting this is a general characteristic of current small/fast models on this task, not specific to one provider.

AreaLimitation
ScaleRetrieval quality has only been benchmarked up to 60 documents; behavior at larger per-tenant graph sizes is not validated in this repository.
Grounding recallThe deterministic verifier layer conservatively drops a third of genuinely correct claims (see Measurable Impact). A model-based layer meant to recover that recall is built and unit-tested, but has no live-provider benchmark run recorded.
Browser Studio securityBinds to loopback only by default, has no authentication, and is not intended for hosted or multi-user use.
Not measuredCost per document or query, and the model-abstention rate across a larger sample than the two real attempts above.

05

How Others Can Use It

Prerequisites

  • Python 3.10+ and uv (or pip).
  • A PostgreSQL 16+ instance with the pgvector extension — the bundled docker-compose.yml provides one, no separate install needed.
  • Optional: OpenAI, Gemini, or LiteLLM Gateway credentials if you want real extraction/answers instead of the built-in offline, deterministic fixture (zero cost, zero network calls).

Repository setup

git clone <url>
cd postgresql-graph-rag
cp .env.example .env
uv sync --extra dev --extra mcp --extra studio
# Export values from .env into this shell (needed by commands using $POSTGRES_URL).
set -a && source .env && set +a
docker compose up -d postgres

--extra studio is required only for the browser demo; --extra mcp only for the MCP server. Omitting either still installs the core library and CLI. On a fresh machine, wait until docker compose ps reports the PostgreSQL health check as healthy before continuing.

Environment configuration

VariablePurpose
POSTGRES_URLAdmin DSN, used once to provision the schema and a restricted runtime role.
PGR_RUNTIME_URLThe restricted runtime DSN created by that setup step; used for every ingestion/retrieval call afterward. Never the admin DSN.
OPENAI_API_KEY / GOOGLE_API_KEYOptional. Set one to use a real provider; leave both unset and pass --provider offline to run at zero cost.
LITELLM_API_KEY, LITELLM_BASE_URL, LITELLM_CHAT_MODEL, LITELLM_EMBEDDING_MODEL, LITELLM_EMBEDDING_DIMENSIONRequired together for --provider litellm. The models are gateway aliases and the dimension must match the embedding alias exactly.

Step 1: provision PostgreSQL and the restricted runtime role

docker compose ps
uv run postgres-graph-rag-demo --admin-url "$POSTGRES_URL" setup --provider offline

This is a one-time, idempotent setup. It creates the secure schema, RLS policies, and the restricted runtime role. It makes no model call. Use --reset only for a disposable demo database because it drops the secure schema and destroys its data:

uv run postgres-graph-rag-demo --admin-url "$POSTGRES_URL" setup --reset --provider offline

Choose --provider gemini for a Gemini Studio database (3072 dimensions), --provider offline/openai for a 1536-dimensional schema, or --provider litellm with LITELLM_EMBEDDING_DIMENSION set to the gateway embedding alias's exact output size. A process must use the same provider and embedding model used to populate its schema; matching dimensions alone do not make embedding spaces interchangeable.

Step 2: run the bundled CLI scenario

uv run postgres-graph-rag-demo --admin-url "$POSTGRES_URL" setup --reset --provider offline
uv run postgres-graph-rag-demo --runtime-url "$PGR_RUNTIME_URL" ingest
uv run postgres-graph-rag-demo --runtime-url "$PGR_RUNTIME_URL" query \
  "Which team owns the dependency of checkout-service?" --mode hybrid_graph

Expected result (re-run for this review): the query prints the retrieved passages, then

Relationships:
- checkout-service --[depends_on]--> auth-service
- deploy-417 --[deployed]--> checkout-service
- auth-service --[owned_by]--> Identity Team
- auth-rollback-runbook --[runs_on]--> auth-service
...

— the checkout-service → auth-service → Identity Team chain, the two-hop fact no single document in the demo dataset states directly. This uses the offline, no-cost extractor; the demo's setup --provider offline|openai|gemini|litellm flag selects which provider's embedding dimension the schema is provisioned for.

Step 3: use the CLI with your own document and question

# CLI, one-shot, scriptable
uv run postgres-graph-rag-demo --runtime-url "$PGR_RUNTIME_URL" playground \
  --provider offline \
  --text "Checkout depends_on Auth." \
  "What does Checkout depend on?"

# Ordinary prose with a real provider (requires a matching schema and API key).
uv run postgres-graph-rag-demo --runtime-url "$PGR_RUNTIME_URL" playground \
  --provider gemini \
  --text "The billing service depends on the ledger service." \
  "What does the billing service depend on?"

# Read a document from a file, return machine-readable output, then clean up.
uv run postgres-graph-rag-demo --runtime-url "$PGR_RUNTIME_URL" playground \
  --provider offline --text-file ./my-document.txt --json --cleanup \
  "Summarize the relevant relationships."

Every Playground invocation gets a fresh tenant and namespace. Offline mode is deterministic and free, but displays retrieval evidence and relationships rather than pretending to generate a natural-language answer. Use --provider openai, --provider gemini, or --provider litellm for composed, cited answers. Add --mode vector, --mode hybrid, or --mode hybrid_graph to compare retrieval behavior; add --top-k and --hops when needed. --cleanup removes that invocation's documents after the result (best-effort document cleanup, not a schema reset).

Step 4: run the Browser Demo Studio

Use a dedicated database for the Studio; do not point it at a database that tests reset or at the bundled scenario database. The following example provisions Gemini once and then launches a Gemini-only Studio process:

# Run from the repository root, with PostgreSQL already healthy.
# Run this once; skip it if graph_rag_studio already exists.
docker compose exec -T postgres psql -U postgres -d graph_rag \
  -c "CREATE DATABASE graph_rag_studio;"
uv run postgres-graph-rag-demo \
  --admin-url "postgresql://postgres:postgres@localhost:5432/graph_rag_studio" \
  setup --provider gemini

export PGR_RUNTIME_URL="postgresql://pgr_demo_runtime:pgr_demo_runtime_pw@localhost:5432/graph_rag_studio"
export GOOGLE_API_KEY="<your Gemini key>"
uv run postgres-graph-rag-studio \
  --runtime-url "$PGR_RUNTIME_URL" \
  --provider gemini \
  --host 127.0.0.1 --port 8501

LiteLLM Gateway alternative (use its own dedicated database/runtime DSN):

export LITELLM_API_KEY="<your LiteLLM virtual key>"
export LITELLM_BASE_URL="https://your-litellm-gateway.example/v1"
export LITELLM_CHAT_MODEL="gpt-5.6-luna"
export LITELLM_EMBEDDING_MODEL="text-embedding-3-small"
export LITELLM_EMBEDDING_DIMENSION="1536"

uv run postgres-graph-rag-demo --admin-url "$POSTGRES_URL" setup --provider litellm
uv run postgres-graph-rag-studio \
  --runtime-url "$PGR_RUNTIME_URL" \
  --provider litellm \
  --host 127.0.0.1 --port 8501

Open http://127.0.0.1:8501. Paste or upload multiple documents, ask a question, then choose Vector, Hybrid, or Hybrid + Graph. “Compare modes” is retrieval-only; generating answers for all modes makes three paid provider calls. The process provider is fixed: switching between Gemini, OpenAI, LiteLLM, and offline requires a separately provisioned matching database and a Studio restart.

For a zero-cost browser run, provision a separate database with setup --provider offline, set its restricted runtime DSN, and launch uv run postgres-graph-rag-studio --runtime-url "$PGR_RUNTIME_URL" --provider offline. Offline Studio can demonstrate ingestion, evidence, entities, and graph traversal, but not arbitrary LLM-generated answers.

Step 5: stop, restart, or troubleshoot

# Stop Studio: press Ctrl-C in its terminal.
# Restart it with the same command after changing code or environment variables.
# If port 8501 is busy:
lsof -nP -iTCP:8501 -sTCP:LISTEN
uv run postgres-graph-rag-studio --runtime-url "$PGR_RUNTIME_URL" \
  --provider gemini --host 127.0.0.1 --port 8502

# Stop PostgreSQL but retain its volume/data:
docker compose stop postgres
# Stop and remove the container (named volume is retained):
docker compose down

Never paste an API key into source control or the browser. The Studio needs only the restricted PGR_RUNTIME_URL, never the admin DSN. If you see a dimension mismatch, use the provider selected during setup or provision a separate database. If you see a missing FastAPI/Uvicorn error, run uv sync --extra studio. The Studio is loopback-only, unauthenticated, and intended for a local single-operator demo.

Try your own text: CLI Playground or browser Studio

# Equivalent minimal commands, after the setup above:
uv run postgres-graph-rag-demo --runtime-url "$PGR_RUNTIME_URL" playground \
  --provider offline --text "Your own document text here." "Your question?"

# Browser Studio -- paste/upload, compare all three retrieval modes side by side
uv run postgres-graph-rag-studio --runtime-url "$PGR_RUNTIME_URL" \
  --provider offline   # http://127.0.0.1:8501, loopback-only

Both accept a live provider instead (--provider openai, gemini, or litellm, with the matching gateway/provider settings), against a schema provisioned for that provider's embedding dimension.

Careful with this one

tests/test_tenancy.py drops and recreates the postgres_graph_rag schema and its runtime roles — point it only at a disposable database, never one with real data. See Limitations for scale and Studio-security caveats.

Reuse it in your own code

  • As a library: engine.add_document(text, namespace, source_id) then engine.answer(question, namespace) — swap the extractor/embedding model via ProviderConfig.
  • With structured data, no LLM extraction cost: add_record() / add_triplets() build the same graph directly from data you already have.
  • As an agent tool: postgres-graph-rag-mcp exposes retrieval, path-finding, and (optionally) ingestion as MCP tools over stdio or HTTP.
